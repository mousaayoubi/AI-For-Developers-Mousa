Proposed Plan

Constraint handling: "No new dependencies" rules out socket.io or ws. I'm proposing Server-Sent Events (SSE) instead of WebSockets:

Backend: plain Node http/Express response kept open with Content-Type: text/event-stream  needs zero new packages.
Frontend: native browser EventSource API  needs zero new packages.
pg (already required to talk to PostgreSQL) is treated as pre-existing, not "new."

Backend

DB migration  add a notifications table: id, recipient_id, actor_id, type, payload (jsonb), is_read, created_at.
Follow endpoint  after a successful follow (must pass existing auth middleware), insert a notification row.
SSE endpoint  GET /api/notifications/stream, gated by the same auth middleware used elsewhere. Unauthenticated request  403 immediately, connection never upgrades to text/event-stream.
Delivery  in-memory map of userId  [response objects] on connect/disconnect. On new follow, if the recipient has an open connection, push an SSE notification event immediately; the row in the DB also lets the frontend fetch missed/unread notifications on load (covers the case where the user wasn't connected at follow-time).
Fan-out across multiple server instances (only if you run more than one Node process)  use PostgreSQL LISTEN/NOTIFY (native to pg, no new dependency) so any instance holding the recipient's SSE connection can pick up the event.

Frontend

On dashboard mount, open new EventSource('/api/notifications/stream', { withCredentials: true }).
On message event, push a toast ("X started following you") and update a notification badge/list in state.
On mount, also GET /api/notifications?unread=true to backfill anything missed while offline.
Mark-as-read on click (existing pattern, small addition).

Risks / Assumptions
Assumption: an auth middleware and follow endpoint already exist and can be reused as-is for the SSE route.
Scaling: the in-memory connection map only works for a single Node process; if you run multiple instances behind a load balancer, you need the LISTEN/NOTIFY fallback (added complexity) or sticky sessions.
SSE limitations: one-directional (serverclient only, which is fine here), and browsers cap concurrent SSE connections per domain (~6 over HTTP/1.1; not an issue over HTTP/2).
Missed events: if the recipient's tab is closed at follow-time, they only see it on next load via the backfill fetch, not "live"  acceptable given the acceptance criteria says "received on the web," not necessarily real-time-while-offline.
Security: SSE endpoint must enforce the exact same auth check as REST routes (cookie/token), and CORS must explicitly allow credentials if frontend/backend are on different origins.
