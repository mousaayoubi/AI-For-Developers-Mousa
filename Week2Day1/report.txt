# Codebase Exploration Report

## Project Summary
An internal web app for training request submission and manager approval. Employees submit requests for courses, certifications, and conferences; managers triage them from an operational dashboard, approve/reject/request info, and leave comments.

## Technology Stack
- React 19 + TypeScript on TanStack Start / Router (file-based routing, SSR-capable via src/server.ts)
- Vite 8 build, Bun lockfile present alongside npm's
- Tailwind CSS v4 + shadcn/ui (full Radix component set in src/components/ui/)
- sonner toasts, lucide-react icons; zod/react-hook-form/recharts are installed but unused by app code
- ESLint + Prettier configured

## Application Entry Points

1. vite.config.ts  the build entry
export default defineConfig({ tanstackStart: { server: { entry: "server" } } })
Everything flows from here. @lovable.dev/vite-tanstack-config bundles the plugins (tanstackStart, viteReact, tailwindcss, tsConfigPaths, nitro, devtools)  the file's comment warns that adding them manually breaks the app with duplicate plugins. The one override redirects Start's bundled server entry to src/server.ts.

2. src/server.ts (61 L)  SSR request entry
Default-exports { fetch(request, env, ctx) }  the Cloudflare-style handler Nitro builds against. It lazily imports @tanstack/react-start/server-entry and wraps it in two layers of error handling: a try/catch, plus normalizeCatastrophicSsrResponse, which exists because h3 swallows in-handler throws into a JSON 500 ({"unhandled":true,"message":"HTTPError"}) that a try/catch never sees. Both paths render renderErrorPage(). Also imports ./lib/error-capture for its side effect at line 1.

3. src/start.ts (29 L)  server middleware config
createStart() registering two request middlewares: an error middleware (re-throws anything with a statusCode, renders the error page otherwise) and a CSRF middleware filtered to serverFn calls. The comment explains the subtlety  Start installs CSRF protection automatically only when this file is absent, so creating the file opts out and it has to be re-added explicitly.

4. src/routes/__root.tsx (126 L)  React app entry
createRootRouteWithContext<{ queryClient }>() with four pieces: shellComponent (the <html>/<head>/<body> document with <HeadContent /> and <Scripts />), component (wraps <Outlet /> in QueryClientProvider), notFoundComponent (404 page), and errorComponent (error boundary that reports to Lovable). The stylesheet enters here via import appCss from "../styles.css?url".

## Major Features

1. Employee request submission (RequestForm.tsx, 286 L)

Nine fields  name, email, department, training title, provider, type, estimated cost, preferred date, justification. Departments and training types come from DEPARTMENTS / TRAINING_TYPES in the data layer, so the dropdowns stay in sync with the schema.

Validation is hand-written (no zod/react-hook-form, despite both being installed) with genuinely useful rules:
- Email format check
- Cost must be  0, and > $20,000 is rejected  "needs a separate budget approval"
- Preferred date can't be in the past
- Justification must be  30 characters  "so your manager can decide"

Two nice UX touches: errors re-validate as you type but only after a field has already failed (no yelling at users mid-entry), and a summary banner counts the failing fields at the top on submit. On success the form clears, the new request is selected, filters reset, and the app jumps to the dashboard with a toast.

2. Status overview tiles that double as filters (StatusOverview.tsx, 72 L)

Six clickable tiles: "All requests" plus one per status. Each shows a count and a state label  "Needs attention" vs "Closed", driven by the open boolean in STATUS_META. The All tile surfaces an openCount ("N still open"). Clicking filters the queue; aria-pressed marks the active one.

3. Request queue with search and filtering (RequestTable.tsx, 150 L)

Two rendered layouts from one component: a card list on mobile, a 7-column table on desktop (lg: breakpoint). Search matches across employee name, training title, department, and request ID. Selected rows get a green left border. Empty state offers a "Clear filters" button rather than a dead end.

4. Detail panel with approval workflow (RequestDetailPanel.tsx, 211 L)

The richest screen. Beyond the field readout and full justification:

- "Next step" callout  each status carries a nextAction sentence telling the manager what to do ("Review the justification and cost, then approve or reject")
- Five actions  Start review (only shown when status is submitted), Approve, Reject, Request more info, Add comment only. Each disables when already in that state.
- Comment-with-decision  text in the box is saved as a comment alongside the status change, in one click. That's the decide() function, and it's the panel's smartest bit of design.
- Manager comments thread with author and date
- Reverse-chronological history  every status change and comment, dot-colored to match the status

5. Status model (trainingRequests.ts)

Five statuses, each with a label, next-action sentence, open flag, and Tailwind classes centralized in STATUS_META:


     Status       Open?         Color        

 Submitted        Yes    Info blue           

 Under Review     Yes    Warning yellow      

 Approved         No     Neo green (primary) 

 Rejected         No     Destructive red     

 Needs More Info  Yes    Neutral gray        


Adding a status means editing this one object  every tile, badge, dot, and filter derives from it.

6. Supporting infrastructure

- 13 realistic mock requests with pre-populated comment threads and activity histories
- Toast feedback (sonner) on every mutation  submission, status change, comment
- Intl-based formatting  formatCurrency (USD, no decimals), formatDate
- Responsive throughout  the dashboard collapses from a 1.4fr/1fr split to stacked below xl:
- 404 and error boundary pages in __root.tsx

What's deliberately absent

No auth or roles  the app trusts whoever's looking, and the manager is hardcoded as "You (Manager)" in the hook. No persistence: every action is lost on refresh. No pagination, sorting, bulk actions, or file attachments.

## External Integrations

The app itself has none. Zero network calls, zero API keys, zero env vars, no .env files. Every byte of data comes from the MOCK_REQUESTS array. The only external systems are platform integrations  build, host, and editor  not application integrations.

## Documentation Gaps

The repo has three doc files, and only one was written for this project: README.md, AGENTS.md (Lovable's git-history warning, 12 lines), and src/routes/README.md (TanStack routing conventions, from the template). No CLAUDE.md, no docs/, no CONTRIBUTING, no LICENSE.

The core problem: the README is the prompt, not documentation

Lines 1117 are the verbatim build brief, in imperative future tense  "Build these main sections," "Managers can," "Use realistic sample data." A new reader cannot tell what exists from what was requested. Everything in it happens to be built, but the document gives no way to know that, and the moment scope changes it becomes actively wrong.

It also never says what the app is in the present tense, has no screenshot, and carries two typos in the spec itself (Mangers, Premuim). Everything after line 118 is Lovable boilerplate.

Gaps ranked by what they'll cost someone

1. The lint landmine is undocumented  highest risk. npm run lint reports 6,281 errors on a clean checkout. 6,275 are CRLF (core.autocrlf=true, no .gitattributes, Prettier defaulting to endOfLine: "lf"). The obvious reaction is npm run format or eslint --fix, which rewrites all ~60 files and syncs a repo-wide diff back to Lovable. Nothing anywhere warns about this. Nothing documents the fix either.

2. Dev server port. README says npm run dev and stops. The Lovable config sets port 8080, not Vite's default 5173. Small, but it's the first thing anyone does.

3. No type-check command. tsc --noEmit passes clean under an unusually strict config (exactOptionalPropertyTypes, noUncheckedIndexedAccess, noPropertyAccessFromIndexSignature). There's no typecheck script and no mention of it  so CI-less contributors will only find type errors at build time.

4. No deployment docs. The build targets Cloudflare Workers via Nitro and emits wrangler.json; npx nitro deploy --prebuilt is discoverable only by reading build output. Not a word in the README.

5. The Supabase seam  the project's central architectural decision  lives in two inline comments. src/data/trainingRequests.ts:5 and useTrainingRequests.ts:27. There's no doc of the intended table schema, how TrainingRequest maps to columns, what happens to the activity/comments arrays relationally, or that @tanstack/react-query is already mounted and waiting for it. This is the most valuable thing to write down and the least written down.

6. Known limitations are unstated. State resets on refresh, no auth, the manager is hardcoded as "You (Manager)", IDs are generated as TR-${1043 + requests.length} (which collides after deletions). All fine for a mock  but a reader has to discover each one by reading source.

7. Nothing explains src/components/ui/. 50 shadcn files, roughly a dozen used. No note saying "template scaffolding, not app code"  so every newcomer and every agent burns time reading them.

8. Installed-but-unused deps mislead. zod, react-hook-form, @hookform/resolvers, and recharts are all in package.json and none are used by app code. A reader reasonably assumes the form is schema-validated; it's hand-rolled. Worth one line either way  document the intent or drop them.

9. Two lockfiles, no statement of which wins. bun.lock (Lovable builds) and package-lock.json (local npm). They can drift  the most recent commit was cleaning up the latter.

## Initial Risks

1. formatDate shows the wrong day for anyone west of UTC. src/data/trainingRequests.ts does new Date(iso) on date-only strings like "2026-08-15". JS parses those as UTC midnight, then Intl renders in local time. Verified:


      Timezone            Renders     

 America/New_York     Aug 14, 2026  

 America/Los_Angeles  Aug 14, 2026  

 Europe/London        Aug 15, 2026   

 Asia/Amman           Aug 15, 2026   


This is invisible from your machine (UTC+3) and hits every date in the app  preferred dates, submitted dates, comment and history timestamps. For an approval tool where "preferred date" drives booking decisions, an off-by-one day is a real operational error. Fix: parse as local (new Date(y, m-1, d)) or format the string directly.

2. The lint/format landmine. 6,275 of 6,281 lint errors are CRLF artifacts (core.autocrlf=true, no .gitattributes, Prettier defaulting to LF). The instinctive fix  npm run format or eslint --fix  rewrites every file and pushes a repo-wide diff straight into Lovable. Undocumented anywhere.

Migration risks

3. The "swap Supabase in without touching components" claim won't survive contact. The seam is well-placed, but it's synchronous. src/routes/index.tsx:145:

const created = createRequest(input);
setSelectedId(created.id);        //  needs the ID immediately

Against a real database, the insert is async and the ID comes back from the server. createRequest, updateStatus, and addComment all return void or a value synchronously, and no component has a loading state, error state, or optimistic-update path. The hook body swaps cleanly; the call sites will still need reworking. Worth knowing before you plan that work as a one-file change.

4. Business rules are buried in the form component. The $20,000 approval ceiling and the 30-character justification minimum live in RequestForm.tsx's validate(). Once a backend exists, these must be enforced server-side too  and they'll drift, because there's no shared schema. zod is already installed and unused; that's the natural home.

5. Auth was deferred, and every manager action is currently unguarded. Fine while it's mock data in a single browser tab. The moment Supabase lands, "Approve" becomes a privileged write that any visitor can call. The manager identity is a hardcoded string ("You (Manager)") in the hook, so there's no user concept to build roles on yet.

6. ID generation is fragile. TR-${1043 + requests.length} collides the instant anything is deleted, and already produces a gap (highest mock is TR-1042; the first new one is TR-1055), suggesting the constant was written against a different list size. Comment and activity IDs use Date.now(), which collides on rapid same-millisecond actions and would produce duplicate React keys.

Stack and process risks

7. Everything is bleeding-edge, and one build dependency is beta. Vite 8, React 19.2, Tailwind 4, TanStack Start 1.168  and nitro: 3.0.260603-beta sits directly in the production build path. Upstream churn in any of these can break the build on a fresh install, with a thin community for troubleshooting.

8. No tests, no CI. Zero test files, no .github/. The only safety net is tsc --noEmit run manually. Any refactor  especially the Supabase migration  is unverified by anything but clicking through the UI.

9. Two lockfiles that can silently diverge. Lovable builds with bun.lock; local dev uses package-lock.json. Add a dependency locally and prod may build without it. The most recent commit was cleanup on the npm side, so this drift is already happening.

10. Lovable coupling constrains normal git practice. No rebasing, amending, squashing, or force-pushing anything already pushed  it corrupts project history on Lovable's side. And since every push syncs into the editor, main must stay in a working state. That rules out the usual "messy commits, clean up before PR" workflow.

## Unknowns and Open Questions

Workflow semantics the code can't answer

How does "Needs More Info" ever resolve? The status exists, managers can set it, and STATUS_META says "Waiting on the employee to answer the manager's question." But there's no employee-facing view, no reply mechanism, and no way to move a request back out of that state except a manager manually approving or rejecting it. The loop is open by design or by omission  unclear which.

Can a rejected request be resubmitted? nextAction says "Closed  the employee can resubmit with new information," but resubmitting means filing a brand-new request with a new ID and no link to the original. Is that intended, or should rejected requests support revision-in-place?

Who sees whose requests? Right now everyone sees everything  the dashboard lists all 12 requests with names, emails, costs, and justifications, and the "New request" form sits in the same UI with no role separation. The README says "Managers can view submitted training requests," which implies a boundary the app doesn't draw. Should employees see only their own?

What happens after approval? "People Ops will handle booking and invoicing"  is there a downstream system, an email, an export, a notification? Or does approval just mean the row turns green?

Business rules with no stated owner

- The $20,000 ceiling  whose policy? What is the "separate budget approval" it points to?
- Budget ownership  the form says "Pick the department that owns the budget," but nothing tracks departmental budgets, spend-to-date, or remaining allowance. Is budget tracking in scope later?
- Approval hierarchy  one manager decides everything today. Does the real process have thresholds (skip-level above $X), or a People Ops second signature?

Backend design decisions still open

If Supabase is the plan, these all need answering before a schema exists:

- Auth provider  Supabase Auth, or corporate SSO/Okta/Google Workspace?
- The user model  are employees and managers rows in a table, or claims from an identity provider? Row-level security depends entirely on this.
- Is department a table or a string? It's a hardcoded array of 8 today.
- Comments and activity  separate tables with foreign keys, or JSON columns? The current shape is nested arrays.
- Retention and PII  this stores employee names, emails, and free-text justifications about people's careers. GDPR/retention obligations?

Environment and operations

- Is Cloudflare Workers the actual deploy target, or just Nitro's default that nobody chose? Is it deployed anywhere today, and who owns the account?
- Will development continue in Lovable, or has it moved local? This decides whether to keep the error-reporting hooks, whether the CRLF fix is safe, and how much the no-force-push constraint matters.
- Locale  formatCurrency is hardcoded USD and formatDate en-US. Single-country org, or does this need multi-currency? (Related to the date bug: what timezones will viewers actually be in?)
- Expected volume  12 mock rows render unvirtualized with no pagination. Is real usage 50 requests a year or 5,000?

Process constraints that may or may not still hold

Is "keep the code understandable for beginners" still binding? It's in the README's constraints, and it directly conflicts with things I'd otherwise recommend  zod schemas, async state machines, test infrastructure. The hand-rolled validate() function reads beautifully because of that constraint. Worth knowing whether it still applies before I suggest replacing it.

Are tests wanted? There are none and no CI. Adding them is cheap now and expensive after the Supabase migration.

## Inferred Information

High confidence  strong evidence, no direct proof

src/components/ui/ is untouched template scaffolding. Basis: components.json present, shadcn naming conventions throughout, and only ~12 of 46 files imported anywhere. I never diffed them against upstream shadcn, so "untouched" is inference  someone could have edited one.

The CRLF situation came from cloning a Linux-authored repo onto Windows. Basis: core.autocrlf=true, no .gitattributes, Lovable builds on Linux, Prettier defaults to LF. The mechanism is textbook and the evidence lines up, but I didn't check whether the files were ever committed with CRLF.

State resets on refresh. Basis: useState(MOCK_REQUESTS) with no persistence layer, no localStorage, no backend. I never actually refreshed the app in a browser to watch it happen.

The Supabase seam is deliberate design, not accident. Basis: two explicit comments naming it, React Query pre-mounted but idle, and all four data operations funneled through one hook. Intent is well-evidenced.

The 6 react-refresh warnings are cosmetic. Basis: they're all "file exports both a component and a constant," which affects Fast Refresh granularity only. Standard, but I didn't test HMR behavior.

Moderate confidence  reasoning, not evidence

npm run format would produce a repo-wide diff that syncs to Lovable. I asserted this as a warning and never tested it  deliberately, since testing means causing the damage. The reasoning is sound (6,275 line-ending violations across ~60 files), but treat it as prediction.

The Supabase migration will require touching components, not just the hook. Basis: index.tsx:145 consumes createRequest's return synchronously, and no component has loading or error states. The code facts are verified; that this will force component changes is my projection about work not yet attempted.

Cloudflare Workers is Nitro's default rather than a deliberate choice. Partly documented  the vite.config.ts comment says nitro is "build-only using cloudflare as a default target"  but whether anyone chose it is inference.

The date bug is invisible to you. Your offset is verified at UTC+3. That you haven't noticed it is an assumption about your experience.

ID collision is latent, not active. Verified: the formula is 1043 + requests.length, and no delete path exists. That it would collide after a deletion is arithmetic; that someone will add deletion is a guess.

Speculative  flagging these as the softest claims I've made

"Training Hub (70)" is a numbered exercise from a prompt set. Basis: the README is a raw build prompt, the title carries a bracketed number, and the commit log is twelve commits literally named "Changes." Suggestive, not conclusive. I built a whole framing around this in the risks answer  if it's wrong, that answer's priorities shift.

The $20,000 ceiling and 30-character minimum reflect real company policy. They might equally be plausible-sounding numbers invented by whatever generated the code. I have no evidence either way, and I treated them as business rules worth preserving.

"Keep the code understandable for beginners" explains the hand-rolled validation. Reasonable  but the generator may simply have written it that way.

Everyone seeing everyone's requests is a privacy problem. The behavior is code-verified. That it's unintended is inference from one README line ("Managers can view submitted training requests").

Editorial, not inference

Worth separating out: calling decide() "the panel's smartest bit of design," describing the dual mobile/desktop layout as deliberate, ranking features as "major," and my priority ordering in the risks answer. Those are judgments. Reasonable people would rank them differently, and none of them are findings.
